# F05 — Временный резерв

## Context & business goal
Как customer, хочу: Не продать один asset дважды.

## Preconditions
F04; valid quote. Выполнить проверку auth/session/tenant до доступа к данным. Пользовательские команды идут через gateway, service credentials не заменяют customer identity.

## Expected behavior / Main scenario
Booking pending -> reserve command; Inventory holds exact assets 10 min.

## Alternative scenarios
Недостаточно units -> rejected; no partial holds.

## Error scenarios
100 concurrent commands contend -> one wins for qty1/one asset. UI показывает стабильный problem code, correlation ID и разрешённое действие. Не раскрывает чужие идентификаторы или stack trace.

## Acceptance criteria
Given one asset; When 100 unique bookings overlap; Then exactly 1 hold, 99 rejections, zero overlapping active allocations.

Записать автоматизированный тест с ID F05, fixture version и фактическим результатом. Снимок UI — дополнение к проверке состояния, а не доказательство транзакции.

## Dependencies and implementation task
F04; этап M05; экраны: checkout,pending. Отдельный PR с review контракта и failure evidence. Для повторных команд и событий действуют общие правила contracts/README.md.
