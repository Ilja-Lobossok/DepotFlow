# F18 — Восстановление после сбоя

## Context & business goal
Как operator, хочу: Довести зависшие операции до результата.

## Preconditions
M08; broker and PSP faults injectable. Выполнить проверку auth/session/tenant до доступа к данным. Пользовательские команды идут через gateway, service credentials не заменяют customer identity.

## Expected behavior / Main scenario
Inspect saga and inbox/outbox; controlled DLQ replay retains event ID.

## Alternative scenarios
Poison payload quarantined with original metadata.

## Error scenarios
Blindly mark success or new charge -> forbidden. UI показывает стабильный problem code, correlation ID и разрешённое действие. Не раскрывает чужие идентификаторы или stack trace.

## Acceptance criteria
Given crash after DB commit before ACK; When restarted and replayed; Then one business effect and no lost transition.

Записать автоматизированный тест с ID F18, fixture version и фактическим результатом. Снимок UI — дополнение к проверке состояния, а не доказательство транзакции.

## Dependencies and implementation task
M08; этап M14; экраны: operations. Отдельный PR с review контракта и failure evidence. Для повторных команд и событий действуют общие правила contracts/README.md.
