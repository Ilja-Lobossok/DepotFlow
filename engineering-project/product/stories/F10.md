# F10 — Возврат и inspection

## Context & business goal
Как operator, хочу: Сохранить состояние оборудования.

## Preconditions
F09; active job. Выполнить проверку auth/session/tenant до доступа к данным. Пользовательские команды идут через gateway, service credentials не заменяют customer identity.

## Expected behavior / Main scenario
Record return once; condition good/damaged; Inventory releases or quarantines; Booking starts settlement.

## Alternative scenarios
Offline dependencies -> queued event; partial returns excluded core.

## Error scenarios
Damage above deposit -> manual_review, no automatic extra debit. UI показывает стабильный problem code, correlation ID и разрешённое действие. Не раскрывает чужие идентификаторы или stack trace.

## Acceptance criteria
When return event delivered 10 times; Then one report, one release, one settlement; damaged asset not bookable until repair.

Записать автоматизированный тест с ID F10, fixture version и фактическим результатом. Снимок UI — дополнение к проверке состояния, а не доказательство транзакции.

## Dependencies and implementation task
F09; этап M09; экраны: return,booking. Отдельный PR с review контракта и failure evidence. Для повторных команд и событий действуют общие правила contracts/README.md.
