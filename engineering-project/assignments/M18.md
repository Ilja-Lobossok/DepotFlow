# M18 — Engineering audit & architecture defense

## Title / Context
Engineering audit & architecture defense. Самостоятельный инженерный этап DepotFlow. Ценность в реальной работе: All F01–F20 and N01–N12 have verified evidence and reviewer verdict. Ориентир трудоёмкости 15–40 focussed sessions по1–3h (архитектура/restore может больше); это planning assumption, не обязательный срок и не обещание результата.

## Learning Objectives
All prior evidence. Уметь объяснить причину выбранного механизма, альтернативу и ограничение до реализации.

## Prerequisites
M17. Прочитать product/business-processes.md и соответствующие service passports/контракты. Перед практикой объяснить незнакомые термины; не копировать готовое бизнес-решение.

## Technical Requirements
Clean install, demo every core journey, independent release, security/resilience/performance/restore, architecture questions.

## Functional Requirements
All F01–F20 and N01–N12 have verified evidence and reviewer verdict. Связанные требования: N12.

## Constraints
Семь независимых владельцев данных; никакого shared database access или подмены backend+worker. Бизнес-код пишет студент. Все retries ограничены, деньги integer, состояния durable, tenant checks server-side. Только sandbox, синтетические данные, isolated lab. Не менять личные VM/credentials/main/remote для выполнения учебного этапа.

## Expected Deliverables
Audit report, demo script, coverage ledger, final ADR updates. Дополнительно: README воспроизведения с местом запуска каждой команды и смыслом аргументов, evidence/M18/manifest.json (commit, image digests, CPU/RAM, dataset seed, UTC time), raw test outputs, ADR если изменились границы.

## Acceptance Criteria
Every requirement evidence link resolves; reviewer independently runs critical races/recovery.

Для каждого связанного F/N требования повторить соответствующий Given/When/Then. Показать независимый запуск теста и состояние после операции, не только HTTP response. Результат = pass/failed/blocked с ссылкой на evidence; непроверенное не pass.

## Testing Scenarios
Positive: All F01–F20 and N01–N12 have verified evidence and reviewer verdict. Negative: forbidden tenant/role, malformed body, unavailable required owner, conflicting operation. Boundary: zero/one/max qty, exact expiry and interval endpoints where relevant. Запустить unique-key повтор и stale version; fixtures в reviews/scenarios.json. Unit tests не заменяют DB/transport experiments.

## Failure Scenarios
Reviewer chooses unexpected fault; no coaching during diagnosis. Записать trigger → observed state → recovery → invariant checks. Рестарт контейнера должен сохранять committed state. Отказ воспроизводится в изолированной среде без удаления чужих данных.

## Review / Audit
Defend every boundary; explain smaller commercial alternative and current trade-offs. Reviewer выбирает один негативный сценарий сам, читает transaction boundary, проверяет ownership credentials и контракт. Нельзя пройти этап только по screenshot/green checkbox.

## Definition of Done
No open integrity/security blockers; unresolved limitations explicit; not merely all task checkboxes. Deliverables доступны, acceptance evidence со стабильными IDs, review замечания resolved или explicit limitation, clean-start инструкции повторены. Правила Ready/Done в operations/engineering-process.md.

## Bonus / Advanced
Interview presentation with measured evidence. Bonus после обязательных проверок; записать ADR и сравнение, не добавлять инструмент без сценария.
