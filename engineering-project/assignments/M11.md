# M11 — Product frontend & notifications

## Title / Context
Product frontend & notifications. Самостоятельный инженерный этап DepotFlow. Ценность в реальной работе: F14/N09 keyboard flows, states, filters, pagination; notifications tenant-scoped. Ориентир трудоёмкости 15–40 focussed sessions по1–3h (архитектура/restore может больше); это planning assumption, не обязательный срок и не обещание результата.

## Learning Objectives
React, accessibility, Redis, SSE. Уметь объяснить причину выбранного механизма, альтернативу и ограничение до реализации.

## Prerequisites
M10. Прочитать product/business-processes.md и соответствующие service passports/контракты. Перед практикой объяснить незнакомые термины; не копировать готовое бизнес-решение.

## Technical Requirements
React typed routes/forms; server state; Notification TS own DB; Redis catalog cache; cursor SSE.

## Functional Requirements
F14/N09 keyboard flows, states, filters, pagination; notifications tenant-scoped. Связанные требования: F14, N09.

## Constraints
Семь независимых владельцев данных; никакого shared database access или подмены backend+worker. Бизнес-код пишет студент. Все retries ограничены, деньги integer, состояния durable, tenant checks server-side. Только sandbox, синтетические данные, isolated lab. Не менять личные VM/credentials/main/remote для выполнения учебного этапа.

## Expected Deliverables
Implemented desktop/mobile UI, Playwright E2E, accessibility report, cache lab. Дополнительно: README воспроизведения с местом запуска каждой команды и смыслом аргументов, evidence/M11/manifest.json (commit, image digests, CPU/RAM, dataset seed, UTC time), raw test outputs, ADR если изменились границы.

## Acceptance Criteria
360px no page overflow; duplicate fact one notification; fresh quote bypasses cache.

Для каждого связанного F/N требования повторить соответствующий Given/When/Then. Показать независимый запуск теста и состояние после операции, не только HTTP response. Результат = pass/failed/blocked с ссылкой на evidence; непроверенное не pass.

## Testing Scenarios
Positive: F14/N09 keyboard flows, states, filters, pagination; notifications tenant-scoped. Negative: forbidden tenant/role, malformed body, unavailable required owner, conflicting operation. Boundary: zero/one/max qty, exact expiry and interval endpoints where relevant. Запустить unique-key повтор и stale version; fixtures в reviews/scenarios.json. Unit tests не заменяют DB/transport experiments.

## Failure Scenarios
Redis down, SSE lost/reconnect, mail sink timeout. Записать trigger → observed state → recovery → invariant checks. Рестарт контейнера должен сохранять committed state. Отказ воспроизводится в изолированной среде без удаления чужих данных.

## Review / Audit
Explain query cache vs business authority; keyboard demo. Reviewer выбирает один негативный сценарий сам, читает transaction boundary, проверяет ownership credentials и контракт. Нельзя пройти этап только по screenshot/green checkbox.

## Definition of Done
All core screen paths and loading/empty/error/denied states tested. Deliverables доступны, acceptance evidence со стабильными IDs, review замечания resolved или explicit limitation, clean-start инструкции повторены. Правила Ready/Done в operations/engineering-process.md.

## Bonus / Advanced
Optimistic UI with explicit rollback. Bonus после обязательных проверок; записать ADR и сравнение, не добавлять инструмент без сценария.
