# M05 — Booking commands & idempotency

## Title / Context
Booking commands & idempotency. Самостоятельный инженерный этап DepotFlow. Ценность в реальной работе: F05/F07 same key same resource, mismatch409; clients poll pending. Ориентир трудоёмкости 15–40 focussed sessions по1–3h (архитектура/restore может больше); это planning assumption, не обязательный срок и не обещание результата.

## Learning Objectives
API operations, transactions. Уметь объяснить причину выбранного механизма, альтернативу и ограничение до реализации.

## Prerequisites
M04. Прочитать product/business-processes.md и соответствующие service passports/контракты. Перед практикой объяснить незнакомые термины; не копировать готовое бизнес-решение.

## Technical Requirements
Booking persists PENDING+outbox, durable request hash; acceptance202; owner lookup endpoint.

## Functional Requirements
F05/F07 same key same resource, mismatch409; clients poll pending. Связанные требования: F05, F07.

## Constraints
Семь независимых владельцев данных; никакого shared database access или подмены backend+worker. Бизнес-код пишет студент. Все retries ограничены, деньги integer, состояния durable, tenant checks server-side. Только sandbox, синтетические данные, isolated lab. Не менять личные VM/credentials/main/remote для выполнения учебного этапа.

## Expected Deliverables
Booking model/state tests, idempotency integration, UI pending draft. Дополнительно: README воспроизведения с местом запуска каждой команды и смыслом аргументов, evidence/M05/manifest.json (commit, image digests, CPU/RAM, dataset seed, UTC time), raw test outputs, ADR если изменились границы.

## Acceptance Criteria
20 repeats create1booking; different tenant same key works.

Для каждого связанного F/N требования повторить соответствующий Given/When/Then. Показать независимый запуск теста и состояние после операции, не только HTTP response. Результат = pass/failed/blocked с ссылкой на evidence; непроверенное не pass.

## Testing Scenarios
Positive: F05/F07 same key same resource, mismatch409; clients poll pending. Negative: forbidden tenant/role, malformed body, unavailable required owner, conflicting operation. Boundary: zero/one/max qty, exact expiry and interval endpoints where relevant. Запустить unique-key повтор и stale version; fixtures в reviews/scenarios.json. Unit tests не заменяют DB/transport experiments.

## Failure Scenarios
Response lost after DB commit; retry vs crash. Записать trigger → observed state → recovery → invariant checks. Рестарт контейнера должен сохранять committed state. Отказ воспроизводится в изолированной среде без удаления чужих данных.

## Review / Audit
Explain 202 vs confirmed and persistence of response. Reviewer выбирает один негативный сценарий сам, читает transaction boundary, проверяет ownership credentials и контракт. Нельзя пройти этап только по screenshot/green checkbox.

## Definition of Done
Idempotency body hash and expiry/replay rules documented. Deliverables доступны, acceptance evidence со стабильными IDs, review замечания resolved или explicit limitation, clean-start инструкции повторены. Правила Ready/Done в operations/engineering-process.md.

## Bonus / Advanced
Multiple-line booking design ADR. Bonus после обязательных проверок; записать ADR и сравнение, не добавлять инструмент без сценария.
