Research & product selection — 11 October 2026

Дата проверки: 2026-10-11, Europe/Tallinn. Метод: целевая качественная выборка страниц работодателей и официальной документации. Это не перепись вакансий и не статистика долей рынка. Поиск смещён к Java, TypeScript и platform; результаты не доказывают превосходство языка или вероятность трудоустройства. География, разрешение на работу, язык и образование требуют отдельной проверки при реальном отклике.

Наблюдения и выводы

R01 показывает ценность фундаментальных знаний и объяснения решений. R02–R06 дают основания тренировать JVM, SQL, API, review и frontend; senior-позиции используются только как ориентир роста. R07–R09 показывают отдельный путь platform: Linux, сети, IaC, контейнеры, инциденты. Название Junior иногда соседствует с требованием 2 лет, поэтому диплом проекта не равен опыту работы. R10 исключена как закрытая страница. Малое число локальных entry-level находок нельзя трактовать как отсутствие спроса.

Главный учебный результат: объяснимые транзакции, контракт API, диагностика сбоя и воспроизводимый deployment. Количество логотипов инструментов не является результатом. Java/Spring выбирается для core-domain; React/TypeScript — для UI; один TypeScript Notification сервис даёт межъязыковую контрактную практику. Kafka не добавляется в основную систему: RabbitMQ лучше соответствует командам и ограниченной нагрузке, Kafka изучается в сравнительной лаборатории.

Сравнение предметных областей

Оценки 1–5 — авторское суждение, не измерения рынка. Критерии: коммерческий реализм (C), естественные границы (M), распределённость (D), бизнес-правила (B), четыре направления (E), соответствие задачам вакансий (J), выполнимость одному (S), защита (I). Вес каждого одинаковый; сумма не скрывает trade-offs.

Выбран DepotFlow: ограниченные физические ресурсы, срок удержания, необратимая выдача и отдельно управляемые платежи дают разные причины распределённости. Это вымышленный продукт с реалистичными правилами, а не утверждение о внутренней архитектуре существующей компании. Для маленького коммерческого стартапа монолит мог бы стоить меньше; здесь микросервисы — явная цель capstone, а границы выбраны по ответственности, а не ради контейнеров.

Исключены: Match Me, marketplace между независимыми арендодателями, реальная обработка карт, налоги по странам, бухгалтерская сертификация, оптимизация маршрутов, IoT. Sandbox PSP и почтовый sink обязательны; настоящие деньги и персональные данные не нужны.

product/PRD.md

DepotFlow — Product Requirements Document v1.0

Платформа для сотрудников и корпоративных клиентов одного арендного оператора с несколькими складами. Мультиарендность — несколько независимых организаций оператора в одном SaaS, клиент принадлежит ровно одной организации. Проблема: обещанное наличие расходится с физическими активами, задержки оплаты и ремонта порождают ручные ошибки. Цель: непротиворечивый путь quote → reservation → authorization → handover → return → settlement с диагностируемыми отказами.

Роли

РольРазрешеноЗапрещено
customerпоиск, свой checkout, свои bookings, отмена до выдачи, свои уведомлениячужие договоры, rates, capture/refund
operatorassets и выдача/возврат только назначенного depotменять тарифы, роли, refund
financepayment/ledger своей организации, refund с причинойвыдача или назначение роли
org_adminmembership, rates, audit своей организацииbypass state machine, ручное изменение ledger
service principalтолько разрешённые internal endpoints/eventsвход в UI и действия от имени customer без subject

Одна активная роль membership; смена роли фиксируется с version. Admin также нуждается в operator membership для физической выдачи (смена роли); superuser обходы запрещены.

Обязательный scope

F01–F20 — все обязательны. Приоритет P0: F01, F04–F12, F16–F18 (целостность и безопасность); P1: F02–F03, F13–F15, F19–F20 (полноценная эксплуатация). Priority означает порядок реализации, не право выкинуть функциональность. Полные stories в product/stories, machine registry requirements/functional.json.

Основные journeys: клиент находит модель и котировку, получает подтверждение либо понятную причину отказа; оператор видит складские jobs, выдаёт и принимает оборудование; finance разбирает неизвестный PSP результат и выполняет ограниченный refund; admin управляет тарифами, доступом и анализирует историю. Корректность — отсутствие двойного выделения, лишнего списания и межtenant утечек; success screen появляется лишь после authoritative business state.

Правила продукта

EUR integer minor units; без налогов в core (цены учебные, не бухгалтерский расчёт). Целые qty 1..5; один model/depot/период на booking. Начало ≥ now+1h; duration 1h..30d; interval [start,end), UTC persistence, UI Europe/Tallinn explicit. Price snapshot на 15 min; hold на 10 min, не продлевается heartbeat. Booking сохраняет quote snapshot, Inventory выделяет конкретные assets. Рабочий день аренды — 24 h, округление вверх; DST не меняет длительность UTC. Sandbox authorization действительна 45d, максимум аренды30d. Partial pickup/return и перенос срока — advanced, не core. Все assets возвращаются одним актом.

Срок просрочки: ceil(max(0, return_at-end_at)/24h), grace15 min (если lateness ≤15 min, late_days0; иначе весь lateness округляется). late_charge=late_days*daily_minor*qty. Damage — целое 0..deposit_minor общей котировки, с заметкой; превышение или capture total > authorized -> manual_review. Capture только после return. Нереальные PSP/тарифы явно подписаны.

Ограничения и допущения

Сервис Fulfillment фиксирует физический факт; потерянный ответ не отменяет состоявшуюся выдачу. При просроченном возврате asset становится unavailable; будущие committed bookings на этот asset получают reconciliation incident, оператор не выдаёт отсутствующий asset и организует ручное замещение/отмену с компенсацией. В core нет гарантии наличия при нарушении клиентом физического срока. Граница учебной и коммерческой инфраструктуры описана в operations/environments.md.

Out of scope / Advanced

Маркетплейс, реальные карты, real invoices, налоговый движок, кредиты, оптимизация маршрутов, геолокация, multi-currency. Advanced: split return, partial capture, replacement saga, Kafka projection, multi-region. Эти расширения не заменяют обязательные failure scenarios.

Success

Все F/N/A требования имеют evidence и независимый audit; нет автоматического обещания production-grade SLA. Система production-like: проектирует коммерческие проблемы и тренирует инженерный процесс в измеренной лаборатории.

product/business-processes.md

Business logic — authoritative process specification

Все часы сохраняются в UTC; deadline проверяет время БД, не браузера. IDs UUID; внешние ссылки принадлежат org. Чтение чужого объекта даёт404; запрещённая операция над своим —403. Проверка membership Tenancy синхронная на каждой изменяющей business command; кеш чтений≤60s. State transition и outbox пишутся одной транзакцией владельца. Inbox уникален (consumer,event_id); ack только после commit. Ниже правила обязательны совместно, не альтернативные варианты.

P01 — Quote

Actors / authorization: customer; Catalog.

Initial conditions: active model/rate; trusted org membership.

Actions / validation: Validate UTC interval, qty; read rate in one transaction, snapshot price and expires_at. Return201 quote ID.

States / concurrency / forbidden transitions: ACTIVE→EXPIRED by time; immutable body. Expired reuse422. Concurrent rate update cannot mix deposit/rental versions.

Retries / cancellation / partial failure / expected outcome: Retry create same key returns same quote. Cancel has no side effect; no money reserved. Catalog/DB fail503; UI re-quotes only after user consent.

P02 — Reserve

Actors / authorization: Booking → Inventory.

Initial conditions: persisted pending booking; valid quote snapshot.

Actions / validation: Publish reserve-requested via outbox; Inventory selects qty assets in ID order, locks asset rows, checks maintenance and allocation overlap, commits all-or-nothing hold+allocation+outbox.

States / concurrency / forbidden transitions: REQUESTED→HELD or REJECTED; HELD→COMMITTED/EXPIRED/RELEASED. Tenant+asset+overlap exclusion, maintenance same allocation table. Failure to acquire any unit rolls back all.

Retries / cancellation / partial failure / expected outcome: Command identity booking_id. Multiple identical commands return same outcome event with stable ID/outbox identity; different parameters409. Expire sweep locks hold, sets allocation inactive; time guard on commit wins over delayed sweep.

P03 — Authorize & commit

Actors / authorization: Booking → Billing → Inventory.

Initial conditions: Held; no cancel requested; deadline=min(holdExpiry, sagaDeadline).

Actions / validation: Billing authorizes rental+deposit using provider_key=booking+authorize:v1. Save authorized result/outbox. Booking publishes commit; Inventory under hold lock checks DB time<expires_at and alloc active; emits committed.

States / concurrency / forbidden transitions: Booking PENDING→CONFIRMED only after allocation.committed AND authorized intent correlation. Expiry or rejection→COMPENSATING→CANCELLED/FAILED after release+void evidence.

Retries / cancellation / partial failure / expected outcome: PSP call may succeed while response lost: UNKNOWN, reconcile query by key; never generate new provider key. Late authorized after compensation -> void. Late committed while cancel intent -> release. Terminal state suppresses stale forward transitions.

P04 — Cancel

Actors / authorization: customer; Booking saga.

Initial conditions: own booking pending/confirmed; no handover claim.

Actions / validation: Atomic booking lock records cancel_requested and version; emit release+void commands if corresponding steps exist. Confirm completion only with observed allocation released and intent voided/no intent.

States / concurrency / forbidden transitions: PENDING/CONFIRMED→CANCELLING→CANCELLED; concurrent handover claim→409. No cancellation after irreversible handover.

Retries / cancellation / partial failure / expected outcome: Repeated same cancellation returns same intent. Partial dependency failure leaves CANCELLING and reconciliation age visible; deadline does not imply compensation success. Cancel-before-hold sets tombstone to reject later hold/commit.

P05 — Handover fence

Actors / authorization: operator; Fulfillment + Booking.

Initial conditions: same depot, confirmed, active allocation, within pickup window.

Actions / validation: Fulfillment calls Booking claim with job_id and expected version. Booking atomic CONFIRMED→HANDOVER_CLAIMED; cancel now forbidden. Fulfillment persists physical act and event; Booking becomes IN_USE after event.

States / concurrency / forbidden transitions: CONFIRMED→HANDOVER_CLAIMED→IN_USE. Claim idempotent per job; another job409. Claim without completed act after timeout→MANUAL_REVIEW, no automatic release.

Retries / cancellation / partial failure / expected outcome: Before physical transfer verify exact serial IDs locally against immutable confirmed allocation snapshot. Lost claim response re-query; never hand over on timeout. Operator must explicitly resolve claim incident; no TTL unlock of possible physical transfer.

P06 — Return & quarantine

Actors / authorization: operator; Fulfillment → Inventory.

Initial conditions: handover act present; same depot; all assets.

Actions / validation: One transaction return report+jobReturned+outbox. Inventory marks original allocation inactive, good asset READY, damaged asset QUARANTINED with maintenance block. Emits allocation.released.

States / concurrency / forbidden transitions: Job IN_USE→RETURNED; Booking IN_USE→SETTLING. Asset READY→RENTED→READY/QUARANTINED. Out-of-order return before handed-over event requires entity lookup/parking.

Retries / cancellation / partial failure / expected outcome: Unique report per job; duplicate same command same report, different body409. If future allocation overlaps new quarantine, do not erase it: mark asset unavailable, incident and notify Booking to stop handover. Settlement blocked until release acknowledged.

P07 — Settle

Actors / authorization: Booking → Billing.

Initial conditions: return report and allocation release; authorized intent.

Actions / validation: Calculate immutable settlement from quote and return. Capture cost≤authorized; void unused authorization. Persist operation IDs/ledger; reconcile unknown PSP separately.

States / concurrency / forbidden transitions: AUTHORIZED→CAPTURE_PENDING→CAPTURED or UNKNOWN; excess→MANUAL_REVIEW. Booking SETTLING→COMPLETED only after captured + remainder void or full void for zero cost.

Retries / cancellation / partial failure / expected outcome: Duplicate settlement operation returns prior amount; changed amount409. Capture+void must reconcile independently. Failure does not reallocate returned equipment. Customer sees settlement pending; no phantom complete.

P08 — Refund

Actors / authorization: finance; Billing.

Initial conditions: captured remainder>0; reason and If-Match.

Actions / validation: Lock intent, reserve refundable amount for pending operation, persist request; invoke PSP stable key outside lock; finalize ledger from response/webhook.

States / concurrency / forbidden transitions: CAPTURED→REFUND_PENDING→PARTIALLY_REFUNDED/REFUNDED; UNKNOWN waits reconciliation. captured-refunded-pending_refunds≥0 invariant.

Retries / cancellation / partial failure / expected outcome: Concurrent full refunds cannot each reserve same remainder. Cancel refund before provider call optional; after call do not assume cancellation. Duplicate signed webhook unique provider_event_id; conflicting payload quarantined.

P09 — Repair

Actors / authorization: operator; Inventory.

Initial conditions: asset not rented; no conflicting committed interval.

Actions / validation: Under asset lock create maintenance allocation, asset QUARANTINED; repair records reason and completed inspection; deactivate maintenance block and mark READY.

States / concurrency / forbidden transitions: READY→QUARANTINED→READY; cannot jump RENTED→READY without return. Future reservation conflicts return409 with dispatcher action.

Retries / cancellation / partial failure / expected outcome: Concurrent maintenance/hold share asset lock and exclusion invariant. Retry same key same maintenance job; changed reason conflicts. Operator access depot-scoped.

P10 — Notification

Actors / authorization: Notification.

Initial conditions: recognized event; valid tenant and subject.

Actions / validation: Inbox dedupe + notification + delivery plan atomic; sender retries mail sink with stable Message-ID; UI SSE sends IDs and cursor.

States / concurrency / forbidden transitions: delivery PENDING→SENT or RETRY→DLQ; read_at independent. Projection versions only advance.

Retries / cancellation / partial failure / expected outcome: Duplicates do not produce duplicate UI rows, but external email can duplicate after ambiguous delivery. Retry 5 attempts; inbox replay policy required when retention reached. Disconnect uses HTTP snapshot, no correctness dependency on SSE.

Booking state machine

PENDING → CONFIRMED | COMPENSATING | CANCELLING; CONFIRMED → HANDOVER_CLAIMED | CANCELLING; HANDOVER_CLAIMED → IN_USE | MANUAL_REVIEW; IN_USE → SETTLING; SETTLING → COMPLETED | MANUAL_REVIEW; CANCELLING/COMPENSATING → CANCELLED/FAILED only after compensation evidence. FAILED/CANCELLED/COMPLETED terminal for forward business changes; late events can still cause compensating commands and audit rows. Refund never changes COMPLETED booking back to SETTLING. Manual review resolutions require reason, role and bounded state transition; no arbitrary status field setter API.

Event ordering rule

Events carry producer aggregate_version and event_id; facts may arrive late. Consumers dedupe by ID and check event-specific prerequisites. Full snapshot projections ignore lower version; business facts are not discarded solely for low version (a late authorization still needs void). Gap -> park event with reason and perform authoritative GET; retry then DLQ if schema invalid. Commands have command_id plus expected correlation, idempotent by business operation; cancellation tombstone prevents resurrection. No total order across services.

Physical overrun

Rental interval conflict guarantees promises based on scheduled return, not physically timely return. Sweep after end+15min for IN_USE assets marks unavailable and emits asset.unavailable; future job handover must reject absent asset. Inventory raises incident listing affected bookings. Dispatcher may cancel before claim or perform advanced replacement saga. Do not automatically refund/replace a physical asset silently. Test overrun against future committed allocation explicitly.

Physical eligibility before claim

Fulfillment GET Inventory /internal/v1/bookings/{booking_id}/handover-check immediately before Booking claim. If not eligible/unavailable, stop; if check succeeds then claim serializes cancellation. Same job serialized at Fulfillment. Inventory consumes handed-over to mark RENTED; late return/handover uses job history not message arrival order. Operator verifies physical serial/condition before actual transfer; this physical check is required even if projection says READY. A failure after claim leaves manual review, not timed auto release.

Membership safety

Tenancy rejects revocation/demotion of last active org_admin with409 last_admin; locks organization and memberships atomically to prevent concurrent removal of two last admins. Invite/role update cannot assign operator without a valid same-org depot. Audit actor/reason/version persists with membership change. Initial org and first admin are synthetic bootstrap fixtures, not open public sign-up in core.

architecture/system-design.md

System design

Семь бизнес-сервисов: Tenancy, Catalog, Inventory, Booking, Billing, Fulfillment, Notification. PostgreSQL database per service, separate roles; один физический instance допустим только dev. Keycloak, gateway, Redis, RabbitMQ, observability — инфраструктура и не считаются бизнес-сервисами. Нет joins, SQL доступов или shared ORM entities между владельцами. Monorepo хранит контракты, но каждый service имеет own build/image/migration/release; общая библиотека допустима для logging/auth plumbing, не domain types.

Sync / Async

Sync: OIDC discovery/JWKS; Tenancy membership checks; Catalog quote; Inventory availability; Booking handover claim; Billing GET reconciliation; пользовательские queries. Async: reserve/authorize/commit/release/void/settle commands и domain facts. RabbitMQ topic exchange depotflow.events + depotflow.commands; один durable queue per consumer, own DLQ; commands адресуются единственному владельцу, events fan-out. Booking — durable orchestrator saga, нет распределённой транзакции.

Outbox DB poller publishes persistent messages with mandatory routing + publisher confirm; mark published only after confirm; unroutable goes operator alert and stays pending. Crash between confirm and mark creates duplicate — ожидаемо. Inbox/business update/outbox commit атомарны; ack после commit. Доставка at-least-once, business effect effectively once under operation invariants; внешняя почта exactly-once не обещается. Local one-node broker не HA, three-node quorum lab даёт majority replication, не multi-region гарантию.

Deadline and compensation

Reserve hold10min, quote15min. Saga begins only on valid quote; deadline=hold expiration after HoldCreated, initial request deadline30s to get hold; missing response triggers owner status query by booking_id. Authorize timeout5s; UNKNOWN reconciliation up to hold deadline then cancellation intent; late auth always void. Commit after expiration rejects even if sweeper lagged. Release command creates tombstone even before original reserve; a delayed reserve cannot resurrect booking. Saga scheduler leases rows and resumes after crash; terminal compensation checked from owner APIs, never inferred from timeout.

Latency budget

External command acceptance ≤500ms target: membership150ms, local DB200ms, gateway overhead50ms, budget reserve100ms. Sync overall deadline2s, connect250ms, request1s for reads; handover claim1s. Max1 retry only for idempotent GET if remaining deadline; writes only stable operation key and owner lookup. PSP call timeout5s, open breaker after5 transport failures in30s, open30s, one half-open probe. Breaker is Billing adapter only: prevents exhausting worker slots, does not make UNKNOWN decline. Async transient retries 1/2/4/8/16s + full jitter[0,base], 5 attempts then DLQ; operator replay original event ID. Backlog oldest age alerts60s; flow control prefetch20, worker concurrency8 first measured then tuned.

Storage / projections

Inventory authoritative concurrency; Booking owns status, Fulfillment physical act, Billing ledger. Read projections explicitly eventual; UI shows updated_at and pending, retry status via GET. Redis only Catalog model-list cache and gateway rate limiter, never allocation correctness. Cache keys include org+filter+cursor+rateVersion; TTL60s, invalidation on catalog.changed; quote calculates from DB, no stale pricing. Redis failure -> bounded SQL read, rate limit local emergency low cap with metric; never fail open on authorization.

Scalability and evolution

Start with HTTP/REST (OpenAPI) and AMQP (AsyncAPI). No gRPC in core: no measured throughput justification and second transport hurts solo debugging. Comparative lab defines protobuf availability query, measures payload/latency and explains why it may remain out of core. Seven Java/Node services fit a lab with constrained memory profiles; do not claim autoscaling from replicas alone. Inventory can partition contention by depot; global date queries need index/query plans before sharding. Keep architecture same while implementing services sequentially.

architecture/diagrams/*.json are editable layout + semantic edges; *.svg are rendered standalone, captions specify design targets, not live deployments. Separate ER per owner and component/sequence/failure variants. diagrams/index.json maps sources to SVG and document.

architecture/technology-decisions.md

Technology map

Core stack is selected, not everything listed is installed. Jenkins, gRPC, Kafka are comparative labs; service mesh, Redis Streams, BullMQ are evaluated alternatives, no mandatory installation. Version locks recorded by student M01; this pack includes no running backend.

Java21 + Spring Boot

Problem: Типизированные domain rules, transactions/security. Decision: use in Backend. Alternatives: Node/Nest, .NET, Go. Limits: JVM memory and library compatibility; pin Boot4.1 patch.

Study: HTTP lifecycle, DI, JDBC transaction boundary. Practice result: M03 quote API and unit/integration suite. Understanding check: Explain rollback when exception is swallowed.

REST / OpenAPI

Problem: Явные HTTP contracts. Decision: use in Backend. Alternatives: gRPC/protobuf lab. Limits: No streaming optimization; breaking semantics need version.

Study: status codes, caching, deadlines, idempotency. Practice result: M06 generated fixtures/provider checks. Understanding check: Explain why POST timeout does not mean failure.

React / TypeScript

Problem: Accessible role-based UI and server-state handling. Decision: use in Frontend. Alternatives: Vue/Svelte. Limits: UI types do not validate network at runtime.

Study: router, TanStack Query, forms, runtime validation. Practice result: M11 checkout and operator E2E. Understanding check: Distinguish UI optimistic cache from booking authority.

PostgreSQL / Flyway

Problem: Owned durable aggregates and interval integrity. Decision: use in Databases. Alternatives: MySQL; ORM; Liquibase. Limits: Physical instance shared dev still has one failure domain.

Study: SQL, MVCC, locks, exclusion, plans, migration. Practice result: M04 contention and query evidence. Understanding check: Explain write skew and why Redis lock is insufficient.

Redis

Problem: Bounded catalog cache and gateway throttling. Decision: use in Caching. Alternatives: in-process, HTTP ETag; no cache. Limits: Eviction and stale data; never inventory truth.

assignments/labs/L01-kafka.md

L01 — Kafka vs RabbitMQ: replayable depot utilization projection

Context / Learning objectives

Mandatory comparison during M14, not a replacement for core RabbitMQ. Understand why a log and a work queue have different replay/ordering/operational costs. Prerequisites M06/M08; outbox/inbox and aggregate versions understood.

Assignment

In isolated Compose profile add one Kafka broker for learning (not HA claim). Topic depot-utilization.v1 with3partitions, key=booking_id. Publish identical contract-approved booking.confirmed and fulfillment.returned facts from isolated archive replay adapter, not dual-publish business transactions to two brokers as production design. Consumer group utilization-v1 writes own projection DB with event_id dedupe and per-booking state. Calculate scheduled asset-hours by depot/day and outstanding returned/not-returned bookings, based on quote UTC period and qty. Returned arriving first parks until booking context known; no negative utilization. Projection is read-only and has no money/availability authority.

Technical / functional requirements

Archive1000bookings with10% repeated event deliveries and randomized order across keys, publish stable IDs; per-key ordering only. Persist projection+dedupe before committing offset. Crash between DB commit and offset commit must redeliver without double-count. Rebalance group with2→3consumers and inspect partition assignment/lag. Start utilization-v2 new group earliest offsets and rebuild identical result within retained history; retention deletion must explicitly demonstrate inability to reconstruct older data without archive/snapshot.

Run equivalent RabbitMQ consumer on same archived input with same DB invariants. Rabbit queue delivery after ACK cannot itself provide full historical replay; replay requires archive publisher. Compare operating complexity, restart behavior, replay time, ordering, payload/throughput and resource usage under the same hardware. No universal throughput winner claimed from one laptop.

Deliverables / acceptance

Topic config, consumer/projection schema, archive seed/hash, event contracts, raw offsets/lag/resource reports, replay comparison ADR. Expected output generated independently from archive offline reduction; final totals exact equality for both. Consumer crash before/after commit and rebalance change no result. Different keys may reorder; prove no global-order assumption. Bad payload goes quarantine with source topic/partition/offset, no infinite poison loop. Retention gap recognized, not zero count silently.

Review / Done / advanced

Reviewer picks offset crash boundary and asks why committing offset first loses data. Explain broker exactly-once claim vs external SQL side effect. Done when comparisons reproducible and limitations recorded; no core saga migrated to Kafka without new ADR. Advanced: transactional producer, compacted snapshot topic, partition count evolution with migration review.

operations/fundamentals.md

Foundations before commands

HTTP request/response: успешный transport response не доказывает завершение async процесса;202 означает durable acceptance,200/201 должны соответствовать обещанному ресурсу. DNS переводит имя в адрес, TCP устанавливает соединение, TLS проверяет шифрование/идентичность, HTTP описывает прикладной обмен. Port — адрес процесса, configured port не доказывает listening socket. Timeout говорит об отсутствии ответа, не об отсутствии выполненного эффекта.

Container изолирует процесс filesystem/network/cgroups, image immutable template, volume хранит данные отдельно от контейнера. Compose описывает локальные зависимости, Kubernetes поддерживает desired state/rollout, но не делает SQL данные автоматически HA. Linux signal SIGTERM просит graceful shutdown; SIGKILL не позволяет дописать транзакцию/ACK. Readiness решает получение трафика, liveness — жив процесс, startup даёт время инициализации.

SQL transaction атомарна внутри одного owner; MVCC позволяет concurrent reads, row lock защищает выбранные строки, isolation level влияет на аномалии. Exclusion constraint ограничивает пересечение двух rows. Index ускоряет конкретный доступ, но увеличивает write cost; EXPLAIN ANALYZE реально выполняет запрос, поэтому эксперимент с writes только lab/rollback. Миграция меняет schema, seed создаёт test data; это разные обязанности.

Redis in-memory key/value хранит cache/throttle; TTL ограничивает stale lifetime, eviction может удалить раньше. Cache не источник правды. Broker переносит сообщение, publisher confirm доказывает приём broker, ACK — признание consumer; ни одно само по себе не financial correctness. Outbox связывает domain write и будущую публикацию, inbox связывает dedupe и consumer effect. Saga — последовательность локальных транзакций с компенсацией; void не тот же DB rollback, физическая выдача может быть необратима.

Idempotency повторяет логический результат для одной operation identity. UUID нового HTTP request не равен business operation key. Retry/jitter ограничивают повтор и синхронизацию клиентов; DLQ хранит нерешённые сообщения, не удаляет проблему. Eventual consistency означает видимый lag projection; UX обязан показывать pending/stale, а correctness проверяется authoritative owner.

OAuth2 регулирует выдачу access, OIDC добавляет identity, JWT — signed token, RBAC — role permissions; проверка роли не заменяет ownership/depot. Trace объясняет одну causal цепочку, metrics показывают агрегаты, logs — события; correlation связывает async процесс. SLO — выбранная цель по определённому SLI/denominator/window; lab target не production SLA.

Git version-controls source, image digest identifies built artifact. CI автоматизирует проверки, CD доставляет проверенный artifact; rollback image не отменяет destructive schema change. OpenTofu state связывает configuration с resources, plan — предполагаемые изменения, apply — реальные; Ansible converges existing hosts. Ни apply, ни изменение личных VM не выполняются автором этого пакета.

Перед любой новой Linux/DevOps командой студент должен указать: где выполнять (Windows editor/Linux lab/repo root/namespace), цель, каждый аргумент, ожидаемый результат, команду доказательства и безопасное восстановление. После ответа тьютор объясняет пробелы; не даёт готовую бизнес-реализацию. Справочные команды будущих tests явно labeled в reviews/test-strategy.md.
